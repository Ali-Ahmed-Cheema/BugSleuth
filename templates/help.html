How BugSleuth works

BugSleuth is designed to help you investigate available evidence, challenge explanations, and review a transparent summary of what is supported and what remains uncertain.

GETTING STARTED

Start a new investigation

From the home page, use the new investigation flow to provide whatever evidence you have available. You do not need to know the root cause before you begin.

BugSleuth can investigate logs, source code ZIP uploads, public GitHub repositories, and a written observation.

  • Choose the type of evidence you want to add
  • Provide logs, source files, a repo URL, or an observation
  • Start the investigation and monitor the evidence review stages
  • Review the findings, tribunal, and verdict
OPTION 1

Try the demo incident

The Demo Incident is a pre-configured sample application and incident included with BugSleuth. It allows you to experience the complete workflow without uploading your own project.

  1. Click “Try Demo Incident” from the home page or navigation.
  2. Watch the investigation phases as BugSleuth collects evidence and analyzes the sample project.
  3. Review the evidence, tribunal arguments, and verdict shown in the dashboard.
  4. Examine the Confidence Ledger and proof section to understand what is established versus what remains uncertain.
  5. Return to the home page using the available navigation controls when you are ready.
OPTION 2

Investigate your own project

GitHub repository

Provide a supported public GitHub repository URL if you want BugSleuth to review a connected project. It can analyze the repository structure, project metadata, supplied history, and project files that are available.

Private repositories are not supported in this prototype. BugSleuth does not execute external code automatically.

ZIP upload

Upload a project ZIP file to provide source code for inspection. The project is analyzed statically, and the supported file size limit is 20 MB.

Uploads are validated, sanitized, and stored temporarily under the local uploads directory. They are not automatically executed.

Log upload

Upload log files or diagnostic output when they contain the most relevant incident evidence. Logs often reveal errors, warnings, timing, and failure patterns.

Replace or update the selected log file if needed before starting the investigation.

You can provide any evidence you have available. BugSleuth will investigate the information supplied and explain what the evidence supports.

REPORTS

Understanding your report

  • Project Intelligence: Details about the project structure, framework, tools, and observed context.
  • Incident Timeline: Chronological events extracted from available evidence.
  • Auditable Evidence: Directly cited material is assigned an E-NNN ID and marked as a Fact.
  • AI Tribunal: The prosecutor, defense, and judge cite evidence, show a causal chain, and challenge assumptions.
  • Judge Verdict: The current conclusion includes uncertainty, the strongest counterargument, and what evidence could change it.
  • Confidence Ledger: Facts, alternative explanations, evidence for and against each hypothesis, and missing information.
  • Verified Proof: The bundled demo can run a real RED → GREEN pytest check against a temporary copy. User code is never executed.
  • DevOps & Delivery Context: Pipeline and deployment signals inferred from project configuration.
  • Code Review Assistance: Similar patterns or risky code areas identified for human review.

The dashboard labels information as Fact, Reasoning, or Verified Proof. Confidence represents the strength of the available evidence, not a guarantee that a conclusion is correct.

MOST_LIKELY

Why does BugSleuth say “Most Likely”?

When evidence is incomplete, BugSleuth can still identify a leading explanation while clearly communicating uncertainty. A MOST_LIKELY verdict means the available evidence suggests this is the strongest explanation, but additional logs, tests, or runtime verification could change the conclusion. The Judge panel names the strongest counterargument and lists the exact evidence that would change the verdict.

SECURITY

Why is execution sometimes unavailable?

BugSleuth does not automatically execute untrusted code from uploaded or external repositories. Executing unknown code can create security risks. The RED → GREEN verification button is available only for the bundled trusted demo and uses a temporary copy; static analysis remains available for user projects.

EVIDENCE & PRIVACY

How your data is handled

This prototype is designed for local use and a controlled investigation workflow. Uploaded logs, source ZIP files, and repository data are processed as evidence for the investigation and stored temporarily under the local uploads directory.

The application checks file size limits, sanitizes uploaded ZIP content, and avoids automatic execution of project code. This is a prototype, and it should not be treated as a production security boundary or a deployment system.

FAQ

Common questions

Do I need to know what the bug is before starting an investigation?

No. BugSleuth is designed to investigate available evidence and help identify possible causes.

Does BugSleuth automatically fix my production application?

No. Any proposed fix should be reviewed and verified by a developer. BugSleuth must never automatically deploy changes to production.

What does “Most Likely” mean?

It means BugSleuth found a leading explanation based on the available evidence, but the conclusion has not been fully proven.

Can BugSleuth be wrong?

Yes. AI-assisted analysis can make mistakes, which is why BugSleuth emphasizes evidence, alternative explanations, and human review.

Why are some investigation features unavailable?

Available features depend on the evidence provided and the security limitations of the environment.
